HOW IT WORKS

From a written brief
to evidence you can replay.

ChaosPilot investigates event-driven systems by proposing unusual message sequences, running them against fresh deterministic simulators, and keeping the traces. Here is the flow, including where its evidence stops.

  1. 01DefineSave a system brief
  2. 02ConfigurePick a target & bounds
  3. 03ExperimentPropose & run sequences
  4. 04InspectVerify, trace, replay

01

Define and save a system brief

Start in the workspace by selecting or creating a system profile, then save its business overview and any additional requirements under Brief & requirements. Saving pins an immutable brief revision to later runs, so editing the profile afterwards never rewrites the evidence of an earlier investigation.

Save or discard edits before launching. Each run uses the saved brief.

02

Choose a target and bounded run settings

Under Prepare investigation, pick one of the available synthetic targets, choose a provider and set the maximum number of experiments. Proposal attempts are bounded too. When a limit is reached, the run stops.

synthetic-trading inventory-reservation other profiles: saved drafts

03

Propose and run event-sequence experiments

The provider proposes structured sequences that can publish, duplicate, reorder, delay or cancel messages and advance logical time. Each experiment runs against a fresh deterministic simulator instance. Nothing carries over between experiments, so a surprising result can be attributed to that sequence rather than leftover state.

order.created→ duplicate→ reorder→ cancel.requested→ invariant check

An illustrative sequence shape. Real experiments are recorded in full in the run's trace.

04

Inspect findings, traces and comparisons

In Findings & reproductions, open a finding to see the exact sequence that triggered it, the recorded message trace, the resulting state, and the brief revision it ran under. Where available, replay re-executes the saved sequence, and a clean-target comparison checks whether the same violation appears without the suspected fault.

A finding is confirmed by replay and a clean comparison, not merely because a sequence looked suspicious.

Three distinctions that keep results honest

Context is not a check

Prose in a brief guides the investigator: it explains what the system is for and what matters. It does not become an executable check.

The adapter's deterministic contract checks, shown under Capabilities & checks, determine which violations an experiment can reveal.

Mock is not a live model

The included scripted mock provider is deterministic and offline. It demonstrates the plumbing; its results are not evidence of autonomous AI defect discovery.

A live model proposes its own experiments and needs a separately configured API key. Its proposals need not be deterministic, but simulator replay of a saved run is.

Synthetic is not your production system

Experiments execute against two built-in synthetic adapters: a trading system (prices, credit, orders, fills, cancellation) and an inventory-reservation system (stock, reservations, shipments, cancellation).

Selecting an adapter always runs that synthetic system, not an arbitrary external production application. Other systems can be described and saved, but remain unconfigured drafts.

What a run does not promise

  • Not every run finds a fault. A run that finishes within its bounds with no violation has not proved the target correct. It shows only that those sequences, under those checks, held.
  • Replay is not a fresh discovery. Replaying a saved run re-executes its recorded sequence without another model call. It checks reproducibility; the result may match or differ.
  • Rejected is not defective. An invalid experiment action is recorded as rejected. It is not, by itself, a target defect.
