# Coverage v1 integration checkpoint

`types.ts` is the authoritative shared schema. `identity.ts` freezes browser-safe catalog/evaluator identities. Public pure function signatures are specified by `CoverageFunctions`; runtime implementations follow in the next commit. No backend/domain changes belong to this branch.

Backend integration owner:

- Implement `POST /api/coverage/prepare` with `CoveragePrepareRequest` / `CoveragePrepareResponse`. Resolve the saved snapshot, adapter target source and canonical contract hash server-side, then call `prepareCoverage`. Reject revision, adapter and target mismatches. Inventory returns no executable suggestions and explicit context-only requirements.
- Accept `coveragePlan` on the existing investigation start request. Call `validateCoveragePlan` against the same saved preparation inputs. Publish the validated plan on `InvestigationRecord.coveragePlan` **before the first provider request**, and echo it in `CoverageLaunchResponse`. Failure to validate must precede any model request. Absent plans on genuine older records remain legacy.
- Record `ExperimentResult.scenarioCheckEvidence` during execution using `ScenarioCheckEvidence`. Its `experimentIndex` is the saved experiment index, not necessarily the array position. Replay must compare the new field and evaluator identity for new records. The UI reads existing `/api/runs` and `/api/runs/:id`; reopening performs no inference or target execution.
- Pass the run's pinned context, requirement mappings and contract rule IDs plus recorded checks, validity, trace references, confirmed findings and stop reason into `projectCoverage`. Do not substitute today's profile/source. The UI can supply coverage fields as parameters until the additive domain fields are integrated.
- Recovery scenario IDs are `recovery-by-deadline` and `recovery-retry-idempotence`. Both may link to the public `recovery_deadline` contract rule, whose exactly-once obligation covers both checks. A separate retry invariant can be linked if present; no invented rule ID is required. Adapter/profile IDs are `synthetic-trading-recovery` / `trading-recovery`.
- Recovery facts identify the target-accepted immutable report/execution/order, acceptance during disconnection, reconnect, inclusive `reconnect + 5` deadline, actual checked horizon/completion, retry observation and expected/observed accounting. A completed deadline check can coexist with an unexercised retry intention. Missing observations or an unreached horizon never prove a pass. `violationId` links a failed check to the actual saved independent oracle violation; only matching reproduced and clean-confirmed findings count as confirmed.

UI and coverage implementation owns only the paths in the session handoff. Backend endpoints, record persistence, runtime observations, replay, launch goals and final combined acceptance remain the recovery session's responsibility. Explicit fixtures exercise development behavior only.
